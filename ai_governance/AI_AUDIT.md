### Flaw 1 – Full review file kept in memory → kernel crash (Module 1 – Yohan ALLOUCHE)
- **AI output:** the file was read "in chunks", but every chunk was kept and concatenated, then duplicates were searched on the whole table:
  ```python
  chunks = []
  for chunk in pd.read_csv(path, usecols=COLS + ["review_id"], dtype=DTYPES, chunksize=2_000_000):
      chunk["date"] = pd.to_datetime(chunk["date"], format="%Y-%m-%d", errors="coerce")
      chunks.append(chunk)
  reviews = pd.concat(chunks, ignore_index=True)   # 41M rows
  dup_rows = reviews.duplicated(subset=COLS).sum()
  ```
- **Problem:** reading in chunks only saves memory if each chunk is reduced before being kept. Here all 41M rows end up in memory: `pd.concat` holds the chunks and the result at the same time (≈ 2 × 0.9 GB), and `duplicated()` builds large intermediate arrays (estimated ≈ 1.5 GB). With about 4 GB of free RAM, the kernel died. Root cause: the AI applied "read the file in chunks" mechanically, without filtering inside the loop.
- **How we detected it:** the notebook stopped with `DeadKernelError: Kernel died` after 82 seconds.
- **Fix:** for the inspection, a development sample (`nrows=5_000_000`). For `reviews_clean`, each chunk is filtered on the sampled games before being kept:
  ```python
  for chunk in pd.read_csv(..., chunksize=2_000_000):
      chunks.append(chunk[chunk["app_id"].isin(release.index)])
  ```
- **Impact:** before: crash, no output. After: the notebook runs; only the reviews of the 10,000 sampled games stay in memory.

### Flaw 2 – Helpful votes and hours played used as early signals → leakage (Module 3 – Jason ZOH)
- **AI output:** the plan written with the AI (`REPARTITION_MODULES.md`, Module 3) lists the "helpful" votes and the hours played among the early signals. The first version of the Module 3 notebook generated by the AI dropped `helpful` but still kept the hours, only flagging them "to check":
  ```python
  signals = window.groupby("app_id").agg(
      n_reviews=("is_recommended", "size"),
      pos_ratio=("is_recommended", "mean"),
      hours_mean=("hours", "mean"),
      hours_median=("hours", "median"),
  )
  ```
- **Problem:** filtering on `days < T` only restricts the **date of the review**, not the date at which the other columns were measured. `helpful` is a vote counter read when the dataset was collected, so a review posted on day 3 carries every vote it received in the following years. `hours` has the same problem: it is the playtime at collection time, not at review time. Both features therefore contain information from after T. Root cause: the AI assumed that every column of a review is measured at the review date.
- **How we detected it:** leakage audit, column by column, asking "is this value known at T?". For `hours`, the describe() of the T = 30 signals showed `hours_mean` up to 903.8 h, more than the 720 h in 30 days. We then checked that 13.6% of the reviews posted in the first 30 days have more hours than the time elapsed since release (`hours > 24 * (days + 1)`), e.g. 149 h two days after release (app 275850).
- **Fix:** `helpful`, `hours_mean` and `hours_median` are removed. `features_T{7,30,90}` only keep `n_reviews`, `pos_ratio` and `has_reviews`. The check stays in the notebook (section 3).
- **Impact:** 13.6% of the early reviews (131,855 out of 972,838) had impossible hours, so the hours features mixed future information into 1,701 games. Effect on the model: <to fill in with Module 4: validation PR-AUC at T = 30 with and without the hours features>

### Flaw 3 – Language lists parsed with `ast.literal_eval` → crash (Module 3 – Jason ZOH)
- **AI output:** to count the languages stored as text lists (`"['English', 'French']"`), the AI read each string as a Python list:
  ```python
  static["n_languages"] = games["languages"].map(ast.literal_eval, na_action="ignore").str.len()
  ```
- **Problem:** the AI assumed the strings were valid Python lists. They are not always: the language `K'iche'` is written with an unescaped apostrophe (`..., 'Kinyarwanda', K'iche', 'Konkani', ...`), which ends the string too early. Root cause: the AI did not check the real content of the column before choosing a parser.
- **How we detected it:** the cell stopped with `SyntaxError: invalid syntax` raised by `ast.literal_eval` on a game supporting 100+ languages. A check on `games_clean` found 67 unreadable lists out of 7,797.
- **Fix:** count the commas instead of parsing the list (no language name contains a comma), and set the empty list `"[]"` to 0:
  ```python
  static["n_languages"] = games["languages"].str.count(",") + 1
  static.loc[games["languages"] == "[]", "n_languages"] = 0
  ```
- **Impact:** before: crash, no feature file. After: `n_languages` is computed for all 7,797 games present in FronkonGames; on the 7,730 readable lists, the comma count gives exactly the same value as `ast.literal_eval`.

### Flaw 4 – Release month and weekday treated as numbers (Module 4 – Lucas GREZES)
- **AI output:** the first pipeline put the release month (1–12) and weekday (0–6) in the numerical columns, imputed and scaled like a price:
  ```python
  NUM_COLS = ["log_price", "required_age", "n_languages", "release_month", "release_weekday",
              "desc_length", "n_reviews", "pos_ratio"]
  ```
- **Problem:** month and weekday are categories, not quantities. For a logistic regression, a numerical month means "the effect grows linearly from January to December", and December (12) is as far as possible from January (1) although they are consecutive. The model can only learn one slope, not "games released in October–November do better". Root cause: the AI put every column with a numerical dtype in `NUM_COLS` without asking what the number means.
- **How we detected it:** code review of the pipeline, column by column, before the oral: "what does a one-unit increase of this variable mean?" For `release_month`, the answer makes no sense.
- **Fix:** one-hot encoding inside the pipeline (fitted on the train only):
  ```python
  CAT_COLS = ["release_month", "release_weekday"]
  (OneHotEncoder(handle_unknown="ignore"), CAT_COLS),
  ```
- **Impact:** validation PR-AUC of the logistic regression before the fix: 0.442 (T = 0), 0.751 (T = 7), 0.811 (T = 30), 0.847 (T = 90). After the fix: 0.435 (T = 0), 0.748 (T = 7), 0.811 (T = 30), 0.848 (T = 90). No measurable gain: the differences are below 0.01 and probably within noise (to be confirmed with the bootstrap confidence intervals of Module 2). The release month and weekday carry little signal. The fix is kept because the encoding is now correct and the coefficients can be interpreted month by month. Lesson: a fix can be right without improving the metric.
