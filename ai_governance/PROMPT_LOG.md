- **Bare prompt (v1):** "I have `recommendations.csv` (41M rows; columns: app_id int, helpful int, funny int, date str YYYY-MM-DD, is_recommended bool, hours float, user_id int, review_id int) and `games.csv` (app_id, title, date_release, win, mac, linux, rating, positive_ratio, user_reviews, price_final, price_original, discount, steam_deck). Write pandas code that loads only app_id, date, is_recommended, hours, helpful from recommendations with compact dtypes (int32, bool, float32), parses dates, and prints shape, dtypes, % missing per column and the number of duplicated rows. Do not drop or impute anything yet. Tell me the expected memory usage and how to read the file in chunks if I have less than 12 GB of RAM."
  → problem with the answer: the code loaded the full 41M-row file into memory and the kernel crashed (see AI_AUDIT, Flaw 1). The answer was also over-engineered (a long helper function computing statistics chunk by chunk) and hard to explain line by line.
- **Constrained prompt (v2):** v1 + "Work on a development sample (`nrows=5_000_000`) instead of the full file. Keep the code minimal: plain pandas calls, no helper functions, no memory estimation. Also load FronkonGames `games_1.csv` with `usecols`, after fixing its header: the column `DiscountDLC count` must be split into `Discount` and `DLC count`, otherwise every column after `Price` is shifted by one."
- **What we kept / changed:** kept the compact dtypes and the date parsing with `errors="coerce"` (unreadable dates become NaT and are counted, not dropped). Removed the memory estimation. Added a note explaining that identical rows are not real duplicates (two players can post the same review values on the same day), so they are not dropped. Checked the FronkonGames alignment with `head(3)`: without the header fix, the `AppID` column contained game names and no game matched Kozyriev; with the fix, 39,436 app_id are shared (77.5% of Kozyriev games).

- **Goal:** produce `reviews_clean.parquet` (app_id, date, days, is_recommended, hours, helpful) and `games_clean.parquet` for Module 2 (target) and Module 3 (features).

  → problem with the answer: it only produced the reviews. A game with zero reviews is absent from `reviews_clean`, so Module 2 could not give it `n_reviews_1y = 0` and would silently drop it (survivorship bias). A `games_clean` table with all sampled games was also needed.
- **Constrained prompt (v2):** "Select the games released between 2015 and 2021 in the Kozyriev games table and draw a random sample of 10,000 app_id (`random_state=SEED`). - **What we kept / changed:** `N_GAMES` is a parameter (`None` = all 2015-2021 games). The release date comes from Kozyriev (base table); the FronkonGames date is only used for the consistency check. An `assert` checks that no review date is unreadable, so that no row is silently lost by the `days >= 0` filter. `dlc_count` and `tags` are kept but flagged as a leakage risk (they may have changed after release), to be discussed in Module 3.

### Entry 4 – Pipeline, baselines and first results table (Module 4 – Lucas GREZES)
- **Goal:** assemble the target and the features for each T in [0, 7, 30, 90], build a scikit-learn pipeline fitted on the train only, and compare a `DummyClassifier` and a logistic regression on the validation set, in order to **choose a baseline model and justify that choice** (improving it is the next step, not this one).
- **Bare prompt (v1):** "Let's move to Module 4: build the baseline."
  → problem with the answer: Module 2 had not delivered `target.parquet`, so there was no label to train on. The request also says nothing about where the imputer and the scaler are fitted, which metric to use with imbalanced classes, or that the test set must not be touched.
- **Constrained prompt (v2):** "Module 2 is not delivered yet: recompute its target with its exact rule (`n_reviews_1y` and `pos_ratio_1y` on reviews with `0 <= days < 365`, left join from all games so that games without reviews get 0 reviews, time-based split 70/15/15 by release date, 80th percentile of `n_reviews_1y` computed on TRAIN only, `success = (n_reviews_1y >= threshold) & (pos_ratio_1y >= 0.8)`). Build one dataset per T in [0, 7, 30, 90] from `features_static` and `features_T{T}`. Build a Pipeline with a ColumnTransformer: numerical features → SimpleImputer(strategy="median") then StandardScaler; binary multi-hot features → passthrough. The pipeline must be fitted on TRAIN only. Models: DummyClassifier(strategy="most_frequent") and LogisticRegression(max_iter=1000, class_weight="balanced", random_state=SEED). Evaluate on VALIDATION with average_precision_score (PR-AUC) on `predict_proba`, roc_auc_score, F1, precision, recall and the confusion matrix. Also print the PR-AUC of a random classifier (= positive rate). Do not use the test set. Save the table to `report/results.csv`. Keep the code minimal."
- **What we kept / changed:** the temporary target gives a threshold of 66 reviews in the first year and about 1 success out of 7 games (13.2% train, 15.7% validation), so accuracy would be misleading and PR-AUC is the main metric. `desc_length` and `n_reviews` are log-transformed (row-by-row, no fitting, so no leakage), as suggested by the Module 3 EDA. Added `zero_division=0` so that the Dummy model (which never predicts a success) gets F1 = 0 instead of a warning. Release month and weekday moved from the numerical columns to a `OneHotEncoder` (AI_AUDIT, Flaw 4). Chosen baseline: the logistic regression (clearly above the Dummy at every T, interpretable through its coefficients, few hyperparameters, handles the imbalance with `class_weight`, gives probabilities); the Dummy is only the floor. The temporary target was then replaced by `target.parquet` (Module 2), so all modules share the same split and threshold.

### Entry 5 – Target definition and time-based split (Module 2 – Arthur DISERBEAU)
- **Goal:** compute `n_reviews_1y` and `pos_ratio_1y` for every game, split the games by release date (70/15/15), define `success` with a threshold computed on the train set only, describe the target per split and over time, and save `target.parquet` for Modules 3 and 4.
- **Bare prompt (v1):** "Compute the success label and split the data into train, validation and test."
  → problem with the answer: nothing forces a time-based split, so a random `train_test_split` is the default answer; nothing says where the top-20% threshold is computed (on all games = leakage); and starting from the review table would silently drop the games with zero reviews (survivorship bias).
- **Constrained prompt (v2):** "Using `reviews_clean` (app_id, date, days, is_recommended) and `games_clean` (app_id, release_date), keep only the games where `release_date + 365 days <= max(review date)`. Compute for each game `n_reviews_1y` and `pos_ratio_1y` using only reviews with `0 <= days < 365`, starting from ALL games with a left join so that games with zero reviews get `n_reviews_1y = 0` instead of disappearing; add an assert that no review outside the window was used. Split the games by release date: oldest 70% = train, next 15% = validation, most recent 15% = test (no shuffling); games released on the same day must fall in the same split. Compute the 80th percentile of `n_reviews_1y` on the TRAIN set only and use it for all splits: `success = (n_reviews_1y >= threshold) & (pos_ratio_1y >= 0.8)`. Print the threshold, the date range and the positive rate of each split, and plot the success rate by release quarter. Keep the code minimal."
- **What we kept / changed:** the split cuts on the release **dates** (70th and 85th percentiles of `release_date`) instead of the rank of the games, so that no release day is shared between two splits (AI_AUDIT, Flaw 6), with an assert that the splits do not overlap. Result: 7,007 / 1,499 / 1,494 games, threshold = 66 reviews in the first year, success rate 13.2% (train), 15.7% (validation), 14.9% (test); 2,200 games (22%) have no review in their first year and are kept as non-successes. The success rate drops in 2017-2018 and rises again from 2019 (distribution shift), so each model must be compared with the random baseline of the same split.
